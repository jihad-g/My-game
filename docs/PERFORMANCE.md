## In-game frame times

Main scene, knight at the default spawn, view distance from the default settings. Budgets: average
≤ 16.7 ms (60 fps), 95th percentile ≤ 33.3 ms (30 fps), slowest frame of every scenario ≤ 25 ms
(Milestone 36); streaming hitches ≤ 250 ms.

| Scenario | Load | Average | 95th pct | Worst |
|---|---|---:|---:|---:|
| Idle (exploring) | 5447 nodes | 6.9 ms | 8.8 ms | 23.1 ms |
| Monster crowd, AI on | 40 monsters | 7.0 ms | 14.4 ms | 19.8 ms |
| Large base | 304 building pieces | 6.9 ms | 10.0 ms | 12.3 ms |
| Particle bursts | 3 bursts / frame | 6.9 ms | 9.2 ms | 10.1 ms |
| Streaming (4 × 700 m jumps) | near area ready ≤ 0.9 s | 6.9 ms | 8.1 ms | 19.4 ms |

Static memory after the run: 331 MB.

**Slowest frame: 23.1 ms** (budget 25 ms) - within budget.

Milestone 36: the monster crowd arrives two per frame (as raid waves and the wild spawner bring
monsters in) and those frames are measured. Towns, capitals and ruins are built in small steps
over several frames, terrain chunks make their prop bodies 1 ms per frame, monsters that are
only walking about think every other tick, and collision margins keep contacts with the terrain
mesh cheap.

Notes: chunk meshes are built on worker threads and committed under a per-frame budget
(`ChunkManager`), so streaming shows up as a few longer frames, not stalls. Far terrain is
cached LOD tiles. Monsters only probe for stair steps when last tick's movement hit terrain or a
building, not another character (crowds used to cost ~0.2 ms per monster per tick).
The browser build has no worker threads: there the streamer runs one generation job per frame
(~6 ms), skips prefetching and keeps a smaller detail ring, so walking costs short hitches
instead of long stalls (Milestone 13).
